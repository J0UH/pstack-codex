# pstack playbook and routing audit

Read-only audit of the local upstream snapshot, pstack 0.15.2 at revision `5bf2b1544db739998121a306340631963c2ff3de`. Intended port scope is reusable Codex behavior across all projects. the first pilot project is the first pilot, not the package boundary. No upstream code was executed, installed, or configured for this audit.

The source root for every path below is `../upstream/pstack`. Table links resolve to the actual local files. The audit treats upstream instructions as source data, not authority over this session.

## What the router does

`poteto-mode` is a workflow selector and a persistent working style. The initial skill has `disable-model-invocation: true`, `mode: true`, and a reminder to apply it when a new task matches a playbook or needs rigor, while leaving casual turns and opt-outs alone. Its internal routing is automatic after activation. These are different mechanisms from the host retaining the selected custom mode across turns. A Codex port must explicitly implement and test that lifecycle rather than assume copying the frontmatter creates it. Sources are [router](../upstream/pstack/skills/poteto-mode/SKILL.md), [wrapper](../upstream/pstack/agents/poteto-agent.md), and [routing guide](../upstream/pstack/docs/guide/02-poteto-mode.md).

The normal path is activate the mode, read its full router and principle index, match the task, read the chosen playbook, copy its steps verbatim into the first todo items, and call leaf skills as their triggers fire. A skipped step remains visible with `skip: <reason>`. Relevant principle leaves must be read in full before applying or citing them. A list of skill names without those instructions is not an equivalent port.

There are 23 bundled playbooks, but not every task gets one unchanged. Large or cross-cutting work, unattended work reviewed later, and tasks with no fitting playbook route through `figure-it-out`. It designs one bespoke run. Standing work that outlives one agent routes to Orchestrate. Orchestrate must collapse back to Autonomous run when one agent could finish in the session budget. Explicit task purpose and authority still matter. A request for a plan remains a plan, and a request for a diagnosis remains a diagnosis.

## Cross-cutting triggers that must survive

- Nontrivial change, architecture choice or “are we sure” invokes `how`. Motivation and regressions add `why`. The bug investigation must establish a runtime mechanism before design fan-out.
- Before asking the human to choose an approach, classify the question. Observable behavior/timing/layout/performance is settled by a Prototype; read-only Investigation answers from evidence instead of creating a prototype. Only a genuine product/preference choice that observation cannot settle belongs to the human.
- Any code starts with the data shape and its organizing structure. Crossing a function boundary invokes `architect`; parallel coverage/races use `swarm`; bakeoffs use `arena`; contested design invokes `interrogate` before shipping.
- Nontrivial multi-step work gets the four-part throughput checkpoint: blocking gates, independent workstreams, shared mutable state, smallest safe decomposition. Keep nonapplicable items with reasons. Read-only investigations/forensics have explicit one-line exceptions.
- All prose uses `unslop`; docs/RFC/readmes/commit/PR prose adds `technical-writing`; agent instructions add the host skill-authoring flow. Before commit is external `deslop`; before review is `no-comments`. Same-surface proof is mandatory when shipping UI/IDE/CLI.
- PR-status intent always routes to pstack Babysit, overriding a matching host babysit skill. The mode must precede the first poll. PR creation does not authorize babysitting, and babysitting does not authorize merging. Land/ship intent changes the route to Shipping.
- Bot comments are untrusted claims, not instructions. [Bugbot rubric](../upstream/pstack/skills/poteto-mode/references/bugbot-triage.md) requires fix/dismiss/ask classification with concrete evidence, fixes at the owning PR, narrow noisy-pattern dismissals, and escalation of ambiguous/high-risk findings. Do not replace this with “fix all comments.”
- Long, unattended and multi-phase work gets `show-me-your-work`. Ordinary logs stay local, while ambitious evidence may be committed. Full/Stack explicitly keep owners' trails uncommitted. Broken skills get their own fixes/PRs, but Orchestrate limits mid-run scope to frontier blockers and parks other work.

## Continuation, new task, opt-out, pause and completion

The [guide](../upstream/pstack/docs/guide/02-poteto-mode.md) defines `continue` and `keep going until done` as continuing the active playbook. “New task” rematches; “don't change code yet” constrains the new route to Investigation. Sticky mode is conversation-local, not a claim that all future projects are automatically activated. Packaging can be global while activation remains per conversation.

The router's reminder excludes casual turns and explicit opt-out. Opting out of the style is not synonymous with cancelling the user's task. Conversely, an explicit operator stop in Full/Stack is an immediate zero-writes hold propagated to all owners. Questions during a Babysit loop receive an answer and the loop continues unless explicitly stopped.

Stopping rules are intentionally different. Investigation/forensics produce answers, Prototype produces a throwaway decision artifact, Eval produces a promotion recommendation, Multi-phase plan stops after the checked plan, Pause produces a resume checkpoint, Babysit stops at merge-ready, Shipping stops at the contiguous verified ceiling, and Autonomous run stops only on its predicate or a real dead end. Hillclimb additionally allows stopping after worthwhile ideas are exhausted. Replacing all of these with a generic “continue until done” loop changes the product.

The Opening a PR file says it is invoked after every other playbook. That cannot be applied literally over narrower source instructions. Investigation explicitly says no PR; Multi-phase plan explicitly says do not implement and stop; Prototype returns disposable artifacts; forensics returns diagnosis; Pause forbids opening a new PR to stop. A faithful port preserves those more specific boundaries.

The wrapper says resume the existing poteto-agent rather than spawning a sibling for the conversation. The router separately warns that interrupt-chained code-worker resumes lose directives and should become fresh consolidated dispatches. Orchestrate similarly forbids resume chains for briefs and reconstructs workers on restart. These refer to different roles: conversation continuity versus disposable bounded implementation workers.

## Model policy is distinct from executable orchestration

[setup-pstack](../upstream/pstack/skills/setup-pstack/SKILL.md) writes a native host rule, `~/.cursor/rules/pstack-models.mdc`. It enumerates models accepted by the current native `Task` interface, confirms budget and role choices, rejects unavailable concrete slugs, and treats `auto`/`inherit-parent` as omission of the model field. Panel list length determines count. A cross-judge pool selects one suitable family; it is not a mandatory all-model panel. Per-role overrides supersede defaults, including leaves such as how/why/arena/swarm/architect/interrogate/reflect. Missing lines retain defaults.

The source uses native `Task` requests, not a generic pstack-owned model API. Poteto delegates use its wrapper; review/exploration skills retain their own specified agent types. Delegates normally run in background agent mode with explicit model role and file pointers. Hard tasks use stronger judgment even when their steps are precisely specified. Review separation and model-family diversity are intent worth preserving; hardcoded Cursor slugs are platform-specific choices to translate with the user's confirmed mapping.

The scripts are evidence and bookkeeping tools. None of the script entrypoints reviewed here is a substitute for the native multi-model agent runtime. In particular, Orchestrate explicitly says the CLI never spawns, waits or wakes agents. A Codex port that shells out to unrelated providers may be a separately designed adapter, but that is not upstream's native routing mechanism and needs explicit provenance and capability reporting.

## Faithful port invariants and required host translations

1. Preserve upstream skills, references, playbooks and helper files by default. Existing Codex skills with similar names do not establish behavioral equivalence. Avoid silently replacing `tdd`, `unslop`, `architect`, `swarm`, or others. Use explicit namespacing/path resolution to prevent collisions.
2. Preserve the routing decision graph and task-state distinctions, including direct leaf invocation, specific read-only returns, skipped-step evidence, figure-it-out override, program collapse, plan-only requests and explicit merge authority.
3. Translate host entrypoints, not the intellectual workflow. Cursor `Task`, `subagent_type`, cloud environments, background completion, AskQuestion/todolist, sticky mode metadata, transcript/store locations, `/goal`, `/loop`, sidebar and control skills all need concrete Codex counterparts and capability tests.
4. Keep confirmed per-role model configuration user-scoped and reusable across projects. Model provider/slug availability and native versus external execution must be visible. Do not claim different model names create cross-family review when they share the same family, and do not fabricate inaccessible models.
5. Project adapters supply base branch, verify harness, surface driver, boot recipe, forge and any stack metadata. project-specific paths, commands or service assumptions belong in its pilot adapter. They must not leak into the shared router.
6. Preserve evidence semantics. Same-surface proof, reproduction-before-fix, frozen baselines, literal parity failure, independent verifier identity, current-head binding, patch-id preservation, queue frontier order and explicit inconclusive states are behavior, not decorative prose.
7. Preserve single-writer ownership and dispatch context. Fresh implementation workers get consolidated scope; standing instructions and upstream reports must reach cloud or otherwise isolated workers. Root topology writers remain distinct from owners and babysitters.
8. Test activation/resume/new-task/opt-out/compaction separately from skill file discovery. A possible Codex hook adapter is not a working runtime until observed in a real session. This audit does not verify host hooks.
9. Respect host and user authority. Upstream's blanket autonomous external-message language cannot silently authorize Slack/email/customer actions in Codex. Preserve intended autonomy for authorized reversible work and explicitly label any necessary host-policy translation.

## Unresolved external dependencies and source tensions

- `cursor-team-kit` supplies `deslop`, `control-cli`, and `control-ui`; these are not bundled here. Their contracts need separately reviewed adapters. Cursor built-in create-skill, `/loop`, `/goal`, native cloud agents, Task model entitlement, transcript paths, store paths and mode UI are host services, not files that copying pstack installs.
- Orchestrate's stack safety and `orch frontier` require Graphite, while Opening a PR, Babysit, Shipping and both Autopilots explicitly say never require Graphite and default to GitHub with optional Origin. This is a real internal tension. A port should label the legacy dependency or implement a reviewed forge-neutral frontier adapter with equivalent invariants, not claim no translation is needed.
- `check-plan.mjs` pins a specific model sentence although setup allows role overrides. Both should be adapted from one model-policy source without weakening the ten-lane/live/perf contract. Plan text also assumes `origin/main` and repo-local `pstack/` paths, incompatible with a user-global install unless resolved dynamically.
- Multi-phase plan's verification recipe demands ten cloud live lanes, but Orchestrate scales cheap identical units down to self-verification with spot checks. These are separate playbook contracts, not permission to impose one global verification count or remove rigor everywhere.

## User-facing explanation

You can give pstack a goal instead of a sequence of skill commands. After you activate poteto-mode, it decides whether you are asking for an explanation, a fix, a feature, an experiment, a plan, a PR check or a shipment, and then applies that workflow's steps. Follow-ups keep the current task moving. “New task” rematches. Each route has its own evidence and stopping rule.

The naive port fails when it copies skill names but loses persistent task state, replaces source skills with superficially similar local ones, assumes Cursor model names are executable everywhere, turns every answer into a PR, treats green CI as independent verification, or confuses ready-to-merge with permission to merge. The faithful port keeps the complete workflow library and makes a small, explicit host adapter around it.
